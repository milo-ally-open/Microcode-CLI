# Model Gateway protocol capability matrix

> This matrix describes the implementation currently present in `src/daemon/protocol/` and `src/daemon/server.ts`. It is a source audit, not a claim of complete vendor conformance. The public Gateway protocol version is `1`; private runtime RPC is separate and currently version `2`.

## Shared gateway behavior

| Area | Current behavior |
|---|---|
| Model selection | Each request resolves one exact `provider/model` identity (Gemini takes it from the route). Unknown models return `404`; Gateway does not fall back to another model. The client dialect does not select the upstream provider API. |
| Authentication | Gateway uses one shared client token. The server accepts a Bearer token, `x-api-key`, or `x-goog-api-key` through a common token parser. There is no per-client identity. The Messages route does not currently validate `anthropic-version`. |
| Request bounds | Public JSON body defaults to 2 MiB and maximum JSON nesting depth is 64. Message/input lists are limited to 500. Function tools are limited to 128; each schema is limited to 65,536 UTF-8 bytes and all schemas in a request to 262,144 bytes. |
| Images | User image input is inline base64 PNG, JPEG, GIF, or WebP. Remote image URLs are not fetched. The selected model must declare image input support. |
| Output limits | `max_tokens`, when present, must be an integer from 1 through 131,072 and cannot exceed the selected model's declared output limit. Temperature is 0–2, top-p is 0–1, top-k is a positive integer, penalties are -2–2, and stop values are strings or string arrays. |
| Tool execution | Function tools are returned as model output; the public Gateway never executes them, reads a workspace, or enters a TUI session. |
| Errors | Before streaming starts, malformed/unsupported requests use HTTP 400; bad token 401; unknown model 404; oversized body/schema 413; concurrency limit 429; provider or unsupported output failure 502; upstream timeout 504. Error JSON is shaped for the selected dialect. Once an SSE response has started, failures are sent as dialect-specific SSE error events. Gemini maps HTTP failures to `INVALID_ARGUMENT`, `UNAUTHENTICATED`, `NOT_FOUND`, `RESOURCE_EXHAUSTED`, `DEADLINE_EXCEEDED`, or `UNAVAILABLE` as appropriate. |
| Streaming | All four routes support their dialect's SSE response. A disconnected client cancels provider work. The default stream idle timeout is 90 seconds; the upstream request timeout is 10 minutes. |

The top-level request object for each dialect rejects fields outside its allowlist, except fields deliberately recognized so the parser can return a specific unsupported-option error. Structured nested objects consumed by the parsers also reject unrecognized fields. JSON Schema bodies, `client_metadata`, and Gemini `functionResponse.response` payloads remain open data shapes by design. Anthropic tool-result content is limited to the text/image structures listed above.

## Per-protocol matrix

| Client dialect | Route and request mapping | Supported response and stream mapping | Explicitly unsupported or constrained behavior |
|---|---|---|---|
| **OpenAI Chat Completions** | `POST /v1/chat/completions`. Roles: `system`, `developer`, `user`, `assistant`, `tool`. Content: text; user inline images; assistant history may contain function calls and `reasoning_content`; tool results are text. Function tools use `type: function`. | Unary response is one assistant choice with text and/or `tool_calls`, finish reason, and usage. SSE emits assistant role, text and function-argument deltas, final usage/finish chunk, then `[DONE]`. Thinking is not included in the response. | Only `n=1`; `parallel_tool_calls=false` is rejected. `tool_choice` supports `auto` and `none`; forced choice is rejected. `response_format`, log probabilities, logit bias, seed, and legacy `functions`/`function_call` are rejected. `reasoning_effort` accepts `minimal`, `low`, `medium`, `high`, `xhigh`, `max`, or `none`; model must support reasoning. `tools[].function.strict=true` requests required JSON Schema constrained sampling; actual availability depends on the selected upstream model/API. |
| **OpenAI Responses** | `POST /v1/responses`. `input` may be a string or an array of message, `function_call`, `function_call_output`, or developer `additional_tools` items. Message roles: `system`, `developer`, `user`, `assistant`; user content may include inline images. Function tools may be namespaced; the explicitly disabled `web_search` marker `{type: "web_search", external_web_access: false}` is accepted for Codex client compatibility. | Unary output contains assistant message/function-call items and usage. Optional reasoning summary output is emitted only when requested and the selected model's API is one of the supported Responses APIs. SSE emits Responses lifecycle events, output-item and function-argument events, then `response.completed`; failures use `response.failed`. | `previous_response_id`, `max_tool_calls`, `prompt`, and `store: true` are rejected; callers must send full input. `tool_choice` supports `auto` and `none`; forced choice is rejected. `parallel_tool_calls: false` limits output to one call. `reasoning.effort` supports `none`, `minimal`, `low`, `medium`, `high`, `xhigh`, or `max`; `reasoning.summary` supports `auto`, `concise`, `detailed`, or `none`. `strict: true` requests required JSON Schema constrained sampling. Hosted tools are not executed. `include: ["reasoning.encrypted_content"]` is accepted but encrypted reasoning is deliberately not returned. `text.verbosity: "low"`, `prompt_cache_key`, and `client_metadata` are validated/accepted but are not forwarded as inference options. |
| **Gemini Generate Content** | `POST /v1beta/models/{provider}/{model}:generateContent` or `:streamGenerateContent`. Roles: `user`, `model`. Parts: text, user `inlineData` image, `functionCall`, and `functionResponse`. Function declarations are supported. | Unary response contains one candidate, text/function-call parts, usage metadata, model version, and response ID. Streaming emits one `GenerateContentResponse` JSON object per SSE data frame, including a final finish/usage frame. | Only one candidate. `generationConfig` accepts `candidateCount`, `maxOutputTokens`, `temperature`, `topP`, `topK`, `stopSequences`, `frequencyPenalty`, `presencePenalty`, and `responseMimeType: "text/plain"`. `toolConfig.functionCallingConfig.mode` accepts `AUTO` or `NONE`; forced function selection is unsupported. Other top-level, generation, tool, and content fields are rejected. Structured output and non-text/image modalities are unsupported. |
| **Anthropic Messages** | `POST /v1/messages`. Roles: `user`, `assistant`; top-level `system` becomes a system message. Content supports text, user base64 image, assistant `thinking`/`redacted_thinking`/`tool_use`, and user `tool_result` with text or image blocks. Function tools use `input_schema`. | Unary response contains text, tool-use, and available thinking blocks with usage and stop reason. SSE emits message/content-block lifecycle events, deltas, `message_delta`, and `message_stop`. Adaptive thinking display may be `summarized` (default) or `omitted`; omitted output retains a signature when available. | `tool_choice` supports `auto` and `none`; forced selection is rejected. Adaptive thinking accepts effort `minimal`, `low`, `medium`, `high`, or `max`; disabled thinking is accepted. Fixed-budget `thinking.type: "enabled"` is rejected. `output_config` is accepted only with adaptive thinking. `context_management`, `container`, and `mcp_servers` are rejected. `anthropic-version` is not validated by the current route. |

## Compatibility evidence and remaining limits

- `tests/daemon/openai-sdk-smoke.test.ts` uses the exact OpenAI Node SDK 6.40.0 against a local Gateway with a deterministic fake model runtime and completes one supported Chat Completions request. This verifies that fixed client request/response path; it does not make a vendor inference request or establish compatibility with every SDK release.
- The optional pinned Codex CLI smoke is a separate boundary test. The CLI reaches the Gateway but submits a hosted `custom` tool which is deliberately rejected, so that smoke does not demonstrate a successful model request or hosted-tool support.
- Fixed protocol fixtures in `tests/daemon/protocol-fixtures.test.ts` cover normalized requests, tool-call/tool-result round trips, per-dialect tool serialization, unsupported-option errors, and ordered stream events. `tests/daemon/protocol-error-stream.test.ts` records each dialect's safe terminal error frames; `tests/daemon/protocol-cancellation.test.ts` verifies client disconnect aborts provider work on all four routes.
- Strict parser checks cover consumed request structures, but do not validate arbitrary JSON Schema, free-form `client_metadata`, or Gemini function-response payloads because those are caller-owned data. Provider/API capability is also model-specific: image, reasoning, output limits and strict-schema support must be checked against the selected descriptor and pinned upstream API.

## Source map

- Routes, shared auth, body/depth limits, concurrency, cancellation, model checks, and error envelopes: `src/daemon/server.ts`.
- Shared content/tool/option parsing and image/schema limits: `src/daemon/protocol/common.ts`.
- Dialect parsers and unary serializers: `openaiChat.ts`, `openaiResponses.ts`, `geminiGenerate.ts`, and `anthropicMessages.ts` under `src/daemon/protocol/`.
- SSE event translation: the corresponding `*Stream.ts` modules under `src/daemon/protocol/` and `src/daemon/streaming.ts`.
- Fixed protocol fixtures: `tests/fixtures/protocols/` and `tests/daemon/protocol-fixtures.test.ts`.
- HTTP cancellation/error fixtures: `tests/daemon/protocol-cancellation.test.ts` and `tests/daemon/protocol-error-stream.test.ts`.
- Broader route and integration cases: `tests/daemon/gateway.test.ts`.
